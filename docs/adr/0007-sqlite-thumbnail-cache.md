# 0007: サーバーサムネイルは SQLite に LRU キャッシュする

- 日付: 2026-08-08
- 状態: 採用

## 文脈

サーバーサムネイルは Riverpod の family プロバイダによるメモリキャッシュ
だけだったため、アプリを再起動するたびに全件を再取得し、オフラインでは
何も表示できなかった（旧 Progress #10）。

永続化先の選択肢は 2 つだった。

1. **SQLite（既存の `flutterbase.db` に専用テーブル）** — 既にスキーマ
   バージョン管理と ffi によるホスト VM テストの仕組みがある。
   バイト数の集計（予算管理）や最終利用時刻による並べ替えを SQL で書ける。
2. **ファイル + インデックス** — 画像をファイルで持ち、パスを DB か
   preferences で管理する。大きな動画ファイルなら有利だが、サムネイル
   （256px で数十 KB）では 2 つの保存先の整合を保つ手間が勝る。

## 決定

**1. SQLite の `media_thumbnails` テーブル（schema v3）に BLOB で保存する。**

- キーは `(account_key, media_id, size)`。メディア ID はサーバーごとにしか
  一意でないため、アップロード履歴と同じ `server#email` でスコープする。
  サインアウト中の読み書きは「ミス扱い」で、失敗にはしない。
- 予算は既定 128 MiB。保存のたびに合計バイト数を確認し、超過分を
  `last_used_at` の古い順（LRU）に削除する。ヒット時に `last_used_at` を
  更新するので、見続けているサムネイルは追い出されない。
- キャッシュの読み書きは `GetMediaThumbnailUseCase`（Application）が
  統括する: キャッシュ優先 → ミス時のみネットワーク → 取得結果を保存。
  キャッシュ層の故障はログして取得にフォールバックし、画面を壊さない。

## 帰結

- グリッドはオフライン・再起動後もキャッシュ済みの範囲で描画できる。
- キャッシュは表示の副産物として貯まる。アルバムの事前一括ダウンロード
  （明示的なオフライン保存）は別機能であり、このキャッシュの上に載せられる。
- BLOB を DB に持つため DB ファイルは大きくなるが、上限は予算で抑えられ、
  アカウント切り替え時も他アカウントの画像が画面に出ることはない。
