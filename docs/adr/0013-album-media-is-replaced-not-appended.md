# 0013: アルバムへの追加は「全置換」で送る（追加専用 API を足さない）

- 日付: 2026-08-10
- 状態: 採用

## 文脈

アルバムの作成・編集をアプリへ入れた（旧 Progress A6）。ADR-0010 は A6 を
「見る」の内側と読んでいる——見たい写真に辿り着く手段だからである。

その実装で最後まで残った判断が、**「この写真をアルバムへ入れる」をどう送るか**
だった。サーバーには追加専用のエンドポイント（`POST /albums/{id}/items` 相当）
が無く、`PUT /api/albums/{id}` の `mediaIds` が**収録メディアの全置換**である。
つまり 1 枚足すには、そのアルバムが今持っている ID を全部読んでから、1 つ足した
配列を送ることになる。

旧 Progress には「大きいアルバムほど往復が増えるので、**この往復を実測してから**
詳細ビューアの導線を決める」と書いていた。実測の代わりに、サーバー側
（`presentation/fastapi/routers/albums.py`）の実装を読んで確定させた結果が次。

- `GET /api/albums/{id}` は `page` / `pageSize` を**省略すると全件を返す**
  （Web フロントエンド互換）。ID を集めるだけなら 1 リクエストで済む。
- ただしその応答は収録メディア **1 件ごとの全レコード**（ファイル名・撮影日時・
  タグ・サムネイル URL）を含む。1 万枚のアルバムでは、ID を知るためだけに
  数 MB を 1 回で受け取ってメモリへ載せることになる。
- `pageSize` の上限は 500。ページ指定なら 1 リクエストあたり最大 500 件で、
  リクエスト数は `ceil(件数 / 500)`。

つまり **往復回数は「1 回」対「500 件ごとに 1 回」**であって、写真 1 枚ごとに
増える類のものではない。当初 Progress が懸念した「往復が増える」は、実際には
「1 回の応答が大きくなる」だった。

## 決定

**追加専用エンドポイントをサーバーへ足さず、アプリ側で「読んで足して全置換」する。**
読み出しは**ページ指定（500 件ずつ）**を使う。

- `AlbumEditingRepository.mediaIdsOf` が `pageSize=500` でページを辿り、
  `EditAlbumUseCase.addMedia` が末尾に 1 件足して `replaceMedia` へ渡す。
- **既に入っている写真は、書き込みを 1 回も出さずに終える。** 同じ集合を
  送り返すのは無害に見えるが、この API は全置換である——読んだ直後に別の端末が
  足した／外した分を、何も言っていない PUT が巻き戻す。並び順（`sort_index`）も
  全行書き換わる。
- **新規アルバムは別扱い**。`POST /api/albums` は `mediaIds` を受け取るので、
  「新しいアルバムを作ってこの写真を入れる」は**1 リクエスト**で済む。作成と
  追加を 2 回に分けない——分けると、2 回目が失敗したとき空のアルバムが残る。

### 全件取得（ページ省略）を採らなかった理由

往復は 1 回で済むが、応答が青天井になる。端末はサーバーと違ってメモリが限られ、
かつ電波の状態が悪い場所で使われる。**境界のある応答を複数回**のほうが、
巨大な応答 1 回より落ちにくい。

### 追加専用エンドポイントをサーバーへ足さなかった理由

`photonest` 側の ADR-0028 と本リポジトリの ADR-0010 が、どちらも「既定は
作らない」を掲げている。今の形で困っている利用者はいない——アプリから
アルバムに写真を入れられないことが問題であって、入れ方が 2 リクエストである
ことは問題として観測されていない。**実際に遅くて困ってから**足す。

## 帰結

- アルバムへ 1 枚追加するコストは、リクエスト数が `ceil(件数/500) + 1`、
  送信するボディがアルバムの全 ID になる。1,000 枚のアルバムで 3 リクエスト。
- **書き込みの境界は閲覧の repository と分けた**（`AlbumEditingRepository`）。
  タグと同じ形で、閲覧しかしない画面が書き込みへ手を伸ばせない。オフライン
  スナップショットは閲覧側にしか無く、書き込みには無い——サーバーが受け取って
  いない変更は変更ではない。
- 「この写真をアルバムへ入れる」の導線は**詳細ビューアのボタン 1 つ**で、
  シートからアルバムを選ぶか新規作成する。画面は増やしていない（ADR-0010
  「タブは 4 つを上限」の内側）。
- **並び順の変更・カバーの指定・公開範囲・共有リンクはアプリへ入れない。**
  サーバーの API にはあるが、「保存する」「見る」のどちらも困っていない。
  次のレビューでこれらを欠落として挙げない（ADR-0010 の制約 3）。
- 全置換である以上、**収録 ID を読み損ねたまま送ると写真が消える**。
  `ApiAlbumEditingRepository` は `mediaIds` が無い応答も、読めない ID が
  1 つでも混じった応答も失敗として扱う（黙って短い配列にしない）。
- 同じ理由から、**要らない書き込みを出さない**ことが安全側になる。他の端末の
  変更を巻き戻す機会は、書き込みの回数だけ存在する。
- **書き込みが済んだ後に読み直さない。** 作成・改名の応答はサーバーが確定させた
  アルバムそのものなので、一覧にはそれを差し込む。ここで一覧を読み直すと、
  その読み込みが失敗したときに「成功した書き込み」がエラー画面や作成前の
  オフラインスナップショットの裏に隠れる。読み直しが要るのはアルバム詳細の
  グリッドだけ（追加した写真の `MediaItem` は手元に無く、サーバーからしか
  得られない）。
- **`album:create` と `album:edit` は別々に判定する。** ピッカーは前者で
  「新しいアルバム」の行を、後者で既存アルバムの一覧を出す。既存アルバムへ
  入れるのは `PUT /albums/{id}` なので `album:edit` が要り、作成しか許されて
  いない主体に一覧を見せると、タップしてから 403 で断られる。
