# 0010: アプリの範囲を「保存する」「見る」に固定し、機能追加を既定で拒否する

- 日付: 2026-08-09
- 状態: 採用

## 文脈

このアプリに求められているのは次の 2 つだけである。

1. 撮った写真を確実にサーバーへ保存したい（自動バックアップ）。
2. 保存した写真を見たい。

一方、開発は「全体レビューで欠落を挙げ、Progress へ起こし、実装する」という
ループで進んできた。欠落は探せばいくらでも見つかるため、このループは放って
おくと機能を増やし続ける。サーバーが API を持っているというだけで「アプリから
触れないのは欠落だ」と書けてしまうのが、特に危うい。

実際、旧 A11（撮影パラメータをビューアに出す）は「サーバーが `exif` を返して
いるのに読んでいない」という理由だけで優先度「中」に載ったが、利用者が求めた
ものではなかった（ADR-0009 で表示しないと決めた）。

## 決定

**アプリの範囲を「保存する」「見る」に固定し、利用者から見た機能を増やす変更は
既定で入れない。**

制約の本文は `CLAUDE.md`「プロダクトの範囲」に置く（作業のたびに読まれるため）。
判断の出所はサーバー側 `photonest` リポジトリの ADR-0028 で、本 ADR はアプリ側の
帰結を記録する。

バグ修正・性能・オフライン耐性・失敗の可視化は対象外とする。これらは機能を
増やさずに「保存する」「見る」の確実さを上げるためである。

## 帰結

- **バックログの見直しを行い、A6・A12・A7 は入れると判断した。** 写真の整理を
  目的とする項目（A6 アルバムの作成・編集、A12 タグの新規作成、A7 アカウント
  設定）を本 ADR に照らしていったん問い直したうえで、**3 件とも実装対象として
  残す**決定をした（2026-08-09）。

  この 3 件は本 ADR の**例外ではなく、範囲の内側にあると読む**。「見る」は
  ライブラリを頭から流し見ることではなく、**見たい写真に辿り着くこと**であり、
  タグとアルバムはその手段である。整理する手段が Web にしか無ければ、写真を
  撮る端末と整理する端末が分かれ、結局あとで PC に向かう手間が要る。A7 は
  自分のライブラリへの入り口を保つ手当（パスワード・二要素）として扱う。

  **この読み替えを他の項目へ広げない。** 「サーバーに API があるのに
  アプリから触れない」は引き続き理由として認めない。A6・A12・A7 は個別に
  判断した結果であって、整理機能なら何でも通るという意味ではない。
- **残る項目の位置づけがはっきりする。** A8（App Link の署名指紋）は「見る」
  への入り口、A9（権限の無い操作を隠す）は失敗の除去、A10（バックアップ対象の
  選択）は「保存する」を意図どおりにする作業であり、いずれも範囲の内側にある。
  A10 は機能追加に見えるが、送るものを**減らす**変更である。
- **タブは 4 つ（写真・アルバム・アップロード・設定）を上限として扱う。**
  増やす提案は本 ADR に照らして判断する。A6・A12・A7 もこの上限の内側で
  作る（A12 は画面を増やさず、A6 はアルバムタブ配下、A7 は設定タブ配下）。
- 次のレビューで「サーバーにこの API があるのにアプリから触れない」を欠落として
  挙げない。触れないことは決めた結果である。
