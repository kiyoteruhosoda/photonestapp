## 詳細

1. **A8 — release 署名のフィンガープリント。** `docs/deep_links/assetlinks.json`
   は `package_name` と debug 署名の指紋まで入っているが、release 分は
   `REPLACE:WITH:YOUR:RELEASE:KEYSTORE:SHA256:FINGERPRINT` のまま。埋まるまで
   release ビルドの App Link は検証されず、リンクはアプリではなくブラウザで開く。
   **鍵を持つ人にしか進められない**ので要判断のまま置く。手順は
   `docs/DEEP_LINKS.md`「`assetlinks.json` の配置」。Play App Signing を使う
   場合は、アップロード鍵ではなく Play Console の「アプリの署名鍵の証明書」の
   指紋を使う。

2. **A9 — 権限の無い操作を隠す。** `AuthSession` はログイン時にサーバーから
   scope を受け取り `hasScope()` まで持っているのに、Presentation 層は一度も
   呼んでいない。結果として `media:tag-manage` を持たない利用者もタグエディタを
   開いてタグを選べてしまい、保存を押した瞬間に 403 で落ちる。削除・お気に入り・
   アップロードも同じ形。`hasScope()` で導線を落とすか、押せないことが分かる
   見た目にする。**サーバー側の変更は要らない**（scope は既に届いている）。

3. **A10 — バックアップ対象の選択。** `SyncNewPhotosUseCase` は端末のライブラリ
   全体を対象にする。`PhotoManagerPhotoLibraryGateway.photosTakenAfter` は
   `onlyAll: true` かつ `RequestType.common` なので、**静止画だけでなく動画も
   すべて含む**。スクリーンショット・メッセージアプリが受信した画像・保存した
   ミームに加え、画面録画や受信動画まで NAS へ上がるため、ライブラリが実際の
   写真で埋もれ、回線とストレージも食う。端末側のアルバム
   （`AssetPathEntity`）単位で対象を選べるようにする——**受け入れ確認は
   写真と動画の両方で行う**（片方だけ見ていると、選ばなかったアルバムの動画が
   上がり続ける取りこぼしに気づけない）。合わせて「充電中のみ」の条件も
   検討する（現状は Wi-Fi 限定の切り替えだけ）。

4. **A6 — アルバムの作成と編集。** 今は一覧と詳細の閲覧だけ
   （`AlbumRepository.findAll` / `findById`）。作成は `POST /api/albums`、
   更新は `PUT /api/albums/{id}`、いずれも `album:create` / `album:edit` scope が
   要る。**収録メディアは差分ではなく `mediaIds` の全置換で送る**
   （`POST /albums/{id}/items` のような追加専用のエンドポイントは無い）。
   「この写真をアルバムへ入れる」を作るなら、対象アルバムの現在の収録を
   全ページ読んでから 1 件足した配列を PUT することになる——大きいアルバムでは
   往復が増えるので、詳細ビューアからの導線を作るかは、その代償を見てから
   決める。境界はタグと同じ形を使える（閲覧の repository とは分ける・結果は
   読み込み済みの状態へ書き戻す・サーバーが確定した値を採る）。画面が要る
   （作成フォーム・編集フォーム）ぶんタグより重い。

5. **A12 — タグの新規作成。** 今できるのは、既にライブラリにあるタグの
   付け外しだけ（`POST /api/tags` を呼んでいない）。新しいタグを起こすには
   Web の管理画面へ行く必要がある。写真を見ている最中に思いついた名前を
   その場で付けられないのは、タグ編集を入れた狙いと噛み合わない。

6. **A7 — アカウント設定。** プロフィール／パスワード変更・TOTP・パスキー。
   いちばん後に置く——写真を見ている最中に必要になるものではなく、Web の
   管理画面でできる。パスキー（`/api/auth/passkeys`）は端末側の WebAuthn 対応が
   要るので、ここだけ切り出して判断する。
