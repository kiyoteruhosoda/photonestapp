# 0012: アプリで作るタグは属性を訊かず「その他」で作る

- 日付: 2026-08-10
- 状態: 採用

## 文脈

タグの新規作成をアプリへ入れた（旧 Progress A12）。今までできたのは、既に
ライブラリにあるタグの付け外しだけで、新しいタグを起こすには Web の管理画面へ
行く必要があった。写真を見ている端末と整理する端末が分かれるのは
`docs/adr/0010-product-scope-save-and-view.md` が「見る」の内側と読んだ状態
そのものにあたる。

ところがサーバーの `POST /api/tags` は `attr`（属性）を**必須**で取る。
`thing` / `person` / `place` / `event` / `scene` / `activity` / `source` /
`others` の 8 種で、空文字や未指定は `invalid_attr` で 400 になる。つまり
アプリは必ず何かを送らなければならない。

一方でアプリのタグエディタは、**写真を見ている最中に開くボトムシート**である。
入り口は詳細ビューアで、閉じれば写真に戻る。ここに「これはどの種類ですか」を
挟むと、タグを 1 つ作るのに検索欄・種類の選択・確定の 3 手が要る。

Web 側（`frontend/src/pages/TagsPage.tsx`）は属性を選ばせているが、あちらは
タグ管理そのものが目的の画面で、前提が違う。

## 決定

**アプリから作るタグは、属性を訊かずに `others` で作る。**

- タグエディタの検索欄で一致するタグが無いとき、候補一覧の先頭に
  「『〇〇』を作る」を出す。タップで作成し、そのまま選択済みにする。
  **画面（ルート）もダイアログも増やさない。**
- 送る属性は `EditMediaTagsUseCase.newTagAttribute`（`TagAttribute.others`）
  に 1 箇所で置く。Infrastructure 層は渡された属性をそのまま送るだけで、
  どれを既定にするかは持たない。
- 属性を後から直す手段はアプリに作らない。Web の管理画面が `PUT /api/tags/{id}`
  で直せる。

## 選択肢と理由

- **案A（採用）: 訊かずに `others`。** `others` は「まだ誰も分類していない」
  ことだけを述べる値で、嘘にならない。写真へ戻るまでの距離が最短になる。
- 案B: 属性を選ばせる。正しく分類されたタグが増えるのは良いが、
  「もの／人／場所／出来事／情景／行動／出所／その他」の違いは、この 8 語を
  見せられた家族には判断できない。結果として大半が「その他」になり、
  操作だけが増える公算が高い。
- 案C: 名前から属性を推測する。人名らしさ・地名らしさの判定を端末に持つのは
  当てにならず、外したときに利用者が直せない（アプリに編集手段が無いため）。
- 案D: サーバーの `attr` を任意にする。サーバー側の契約変更が要り、Web の
  一覧・絞り込みが「属性なし」を扱えるようにする波及がある。アプリの都合で
  サーバーの契約を緩めるのは順序が逆。

## 影響

- **良い点**: タグを作るのはタップ 1 回になる。作成に必要な権限は
  `media:tag-manage` だけで、タグエディタを開けている時点で満たしている
  （サーバーは付け外しと同じ scope を要求する）ため、権限の出し分けは要らない。
- **トレードオフ**: アプリ発のタグは属性の情報を持たない。候補一覧では
  「その他」と表示される。分類が要るときは Web で直す。
- **同名は増えない**: サーバーは大文字小文字を無視して既存名を照合し、
  既にある名前には既存のタグをそのまま返す（`created: false`）。アプリ側も
  同じ比較で「作る」の提示可否を決めるので、押しても何も起きない状態にならない。
- **作って保存せずに閉じると、タグだけがライブラリに残る。** タグは
  メディアより先に存在しないと結び付けられないため、作成だけは保存を待たずに
  サーバーへ届く。サーバーはメディアから外れたタグを掃除するが（付け外しの
  経路）、一度も付いていないタグはその対象にならない。実害は Web のタグ一覧に
  未使用のタグが並ぶことだけなので、これを避けるための仕組みは入れない。
